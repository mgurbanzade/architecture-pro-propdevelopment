# Проверочный лист безопасности бизнес-систем PropDevelopment

Лист составлен по шаблону из урока "Составление проверочного листа" и заполнен по описанию компании и диаграмме контейнеров C4.

Значения в колонке "Да/нет":
- **Да** - мера есть;
- **Нет** - меры нет, это следует из описания или диаграммы;
- **Частично** - мера есть не везде или не полностью;
- **Нет данных** - в материалах нет информации, в комментарии указано, что проверить на аудите.

## 1. Системы и их работа с точки зрения безопасности

| Система | Домен | Данные | Кто и как обращается | Что важно для ИБ |
| --- | --- | --- | --- | --- |
| Витрина продаж (React) | Продажи | Каталог, данные бронирования, контакты клиента | Клиенты из интернета через firewall | Публичная точка входа. Отсюда клиент регистрируется в auth-service-1 и client-crm-app, это одна из нескольких точек регистрации |
| auth-service-1 (Keycloak) + auth-db-1 | Продажи / ЖКУ | Учетные записи покупателей и собственников, пароли, сессии | Витрина продаж и мобильное приложение собственников, REST | Единственный сервис аутентификации внешних пользователей. | client-crm-app (Dynamics CRM, ElasticSearch) + crm-db (MSSQL) | Продажи | ПДн клиентов: карточка, профиль, история | Витрина (регистрация, карточка, профиль), менеджеры через AD | Главное хранилище ПДн клиентов. Публикует каталог объектов в Kafka. Отдает сырые данные в хранилище по CDC |

| client-tour-app + client-tour-db | Продажи | 3D-туры, результаты осмотров | Витрина, REST. Каталог из Kafka | Риск ниже: в основном публичный контент |

| tenant-core-app + tenant-core-db | ЖКУ | Услуги ЖКУ, начисления, ремонты | Мобильное приложение (REST, WebSocket). Поставщики ресурсов ЖКХ и платежная система | Через этот сервис идут API партнеров (управляющих компаний) без единых политик ИБ. CDC в хранилище |
| CRM ЖКУ + crm-tenant-db | ЖКУ | ПДн собственников | tenant-core-app (REST), менеджеры через AD | Вторая независимая CRM: клиент-покупатель и собственник - разные записи. CDC в хранилище |
| accountant-service-1 + auth-db-1 | Финансы | Бухгалтерский учет | Бухгалтер, аутентификация через AD | Коммерческая тайна. Финансовый домен закрыт отдельным AD |
| Active Directory (2 экземпляра) | Общие | Учетные записи сотрудников | Менеджеры, бизнес-аналитики, бухгалтер | Два независимых каталога плюс Keycloak: единого реестра учетных записей нет |
| Хранилище данных (Greenplum) + DWH (S3) | Дата | Сырые CDC-копии 5 продуктовых БД | Бизнес-аналитики через AD, BI-аналитики напрямую | Все ПДн компании в одном месте без обезличивания. По описанию, доступ к данным здесь не ограничен |
| Поставщики ресурсов ЖКХ, управляющие компании | Внешние | ПДн собственников, начисления, данные домов | API партнеров | В контрактах API есть ПДн. Партнер одной УК видит и меняет данные другой |
| Платежная система | Внешняя | Платежные данные | tenant-core-app | Внешний обработчик платежных данных |
| Государственные регистрационные органы | Внешние | Документы сделки | client-mart-app через СМЭВ (SOAP) | Юридически значимый обмен, нужны ключи ЭП |

Расхождения в самой диаграмме, которые стоит уточнить на аудите. Они показывают, что архитектурная документация не поддерживается в актуальном виде:
- у двух AD описания перепутаны: AD "для финансовых сервисов" аутентифицирует менеджеров и бизнес-аналитиков, а AD "для прикладных систем и обработки данных" стоит в финансовом домене;
- accountant-service-1 подписан как Keycloak, а его БД называется auth-db-1, как БД сервиса аутентификации покупателей;
- у аналитика BI на диаграмме нет аутентификации при доступе к хранилищу данных.

## 2. Какие разделы включены и почему

Разделы выбраны по двум главным проблемам компании (нарушен контроль данных, небезопасные API партнеров) и четырем целям аудита (жалобы клиентов, продукты на данных, предотвращение утечек, соответствие закону).

| Раздел | Включен | Почему |
| --- | --- | --- |
| I. Управление доступом | Да, полностью | Причина жалоб "в личном кабинете чужие ФИО" и межтенантного доступа партнеров - в управлении учетными записями и авторизацией. Учетные записи ведутся в трех местах (2 AD, Keycloak), а в хранилище данных доступ не ограничен |
| II. Безопасность данных | Да, полностью | Это главная проблема компании. Классификации и Data Governance нет, ПДн дублируются и сырыми уходят в хранилище. Без этого не запустить продукты на BI/ML/AI и не предотвратить утечку, как у конкурента |
| III. Защита инфраструктуры | Да, полностью | Инфраструктура гибридная (свой ЦОД, частное облако, арендованные мощности). Команды временно берут облачные ресурсы для разработки и тестов, поэтому важны сегментация, периметр и контроль облачных конфигураций |
| IV. Управление инцидентами | Да, полностью | Руководство беспокоит утечка у конкурента. 152-ФЗ требует сообщить в Роскомнадзор об утечке ПДн в течение 24 часов. Жалобы клиентов на чужие данные - фактически инциденты, их нужно расследовать |
| V.1. Общие вопросы | Частично: VPN и облачные резервные копии | Удаленный доступ и резервные копии в облаке относятся к гибридной инфраструктуре. MDM и контроль неавторизованных устройств исключены: о корпоративных устройствах в материалах нет данных, к заявленным проблемам они не относятся. Их стоит проверить отдельным аудитом рабочих мест |
| V.2. Оборудование и физическая безопасность | Нет | Проблемы компании связаны с данными и интеграциями, а не с помещениями и оборудованием. Свой ЦОД есть, но данных о нем нет. Физическую безопасность лучше проверить отдельным аудитом ЦОД. Удаление данных с носителей учтено в вопросе II.10 |
| VI. Интеграции и API партнеров | Добавлен | Вторая главная проблема из описания: API управляющих компаний без единых политик, избыточные ПДн в контрактах, межтенантный доступ. Компания планирует развивать партнерские сервисы, в том числе "Умный дом" |
| VII. Соответствие законодательству РФ | Добавлен | Отдельная цель аудита. Ландшафт рос за счет новых интеграций, и нет уверенности, что процессы соответствуют 152-ФЗ |
| VIII. Процессы управления ИБ | Добавлен | Специалист по ИБ один на компанию, после смены руководителей команд до него доходят не все решения. Без процесса любые технические меры быстро устареют |

## 4. Главные выводы

1. **Изоляция партнеров в API (I.7, VI.4) - критично.** Межтенантный доступ уже обнаружен: это утечка и искажение ПДн собственников. Нужны API Gateway, аутентификация партнеров и проверка принадлежности объекта к УК при каждом запросе.
2. **Нет единого реестра клиентов и учетных записей (I.11, II.11) - критично.** Несколько несогласованных точек регистрации - наиболее вероятная причина показа чужих данных в личном кабинете. Нужны единый идентификатор клиента (MDM) и связка учетной записи Keycloak с карточкой клиента.
3. **Сырые ПДн в хранилище без ограничений (II.8, II.13) - критично.** Это самый крупный концентратор ПДн, и именно он блокирует продукты на BI/ML/AI. Нужны классификация, обезличивание при загрузке и доступ по ролям и меткам.
4. **Изменения не доходят до ИБ (VIII.2).** Без этого процесса выводы аудита быстро устареют. Нужны обязательное ревью ИБ и ответственные в командах.
5. **Соответствие 152-ФЗ не подтверждено (раздел VII).** В первую очередь проверить согласия во всех точках регистрации, актуальность уведомления в Роскомнадзор и процедуру уведомления об утечках.
