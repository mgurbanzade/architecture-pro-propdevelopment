# Требования к внешним интеграциям: сервисы "Умный дом"

Новые бизнес-функции для собственников:
- **Интеллектуальный домофон** - видеовызов в квартиру с открытием двери из приложения и автоматическое открытие по лицу жильца.
- **Интеллектуальный шлагбаум** - открытие из приложения и автоматический въезд по распознанному номеру автомобиля.

Функции предоставляет партнер. Собственники пользуются ими через текущее мобильное приложение.

## 1. Распределение ответственности

| Кто | За что отвечает |
| --- | --- |
| Партнер | Оборудование в ЖК (вызывные панели, камеры, замки, контроллеры шлагбаумов), облачная платформа, медиасервер для видеовызовов, распознавание лиц и номеров, хранение биометрических шаблонов |
| PropDevelopment | Аутентификация собственников, интерфейс в мобильном приложении, **решение о том, у кого есть доступ** (жильцы, гости, автомобили), согласия на биометрию, журнал событий, связь с данными о собственниках |

Главный принцип: PropDevelopment - источник истины о правах доступа, партнер их исполняет. Так компания сама контролирует, кто может войти в дом, и при смене партнера не теряет данные о правах.

| Элемент | Изменение | Зачем |
| --- | --- | --- |
| **API-шлюз внешних интеграций** (Kong) - новый | Единая точка входа и выхода для всех партнеров: платформа "Умный дом", управляющие компании, поставщики ЖКХ, платежная система | Закрывает проблему API партнеров из описания: одни политики аутентификации, авторизации и лимитов для всех. Журнал всех вызовов |
| **smart-home-app** + **smart-home-db** - новые | Сервис "Умный дом": права доступа, согласия, команды открытия, прием событий от партнера, журнал | Логика доступа и чувствительные данные живут в отдельном сервисе с отдельной БД, а не в tenant-core-app |
| **Хранилище секретов** (Vault) - новое | Сертификаты mTLS, ключи и токены партнеров, их ротация | Секреты интеграций сейчас хранятся без единых политик (задание 2, раздел VI) |
| Мобильное приложение собственника - изменено | Раздел "Умный дом": прием вызовов, открытие двери и шлагбаума, управление доступом, согласия | Новые функции доступны в текущем приложении |
| tenant-core-app - изменен | Вызовы поставщиков ЖКХ и платежной системы идут только через API-шлюз | Убираем прямые неконтролируемые интеграции |
| CRM ЖКУ - изменена | API состава жильцов квартиры и событие "смена собственника / выезд жильца" | smart-home-app проверяет, что пользователь живет в квартире, и автоматически отзывает права |
| Хранилище данных | **Без изменений**: smart-home-db не подключается к CDC | Биометрия, журнал проходов и номера машин не должны попадать в общее хранилище, где доступ не ограничен |
| Платформа "Умный дом" партнера, сервисы push-уведомлений - новые внешние системы | Видео, распознавание, устройства. Доставка вызова на телефон | |

## 3. Данные интеграции и их классы

Классы - по классификации из задания 1.

| Данные | Класс | Где хранятся | Что получает партнер |
| --- | --- | --- | --- |
| Биометрические шаблоны лиц жильцов | Секретные (биометрические ПДн) | Только у партнера, в РФ, в зашифрованном виде | Создает сам из фото |
| Фото лица для регистрации | Секретные | Не хранится в PropDevelopment: приложение отправляет его напрямую партнеру | Фото, удаляется после создания шаблона |
| Видеопоток и записи с вызывных панелей и камер | Конфиденциальные | У партнера, ограниченный срок хранения | - |
| Права доступа (квартира, подъезд, шлагбаум, срок) | Секретные (доступ в жилище) | smart-home-db - источник, копия у партнера | Псевдонимный ID жильца, ID объекта, срок |
| Номера автомобилей, связанные с собственником | Конфиденциальные (ПДн) | smart-home-db | Только номер, шлагбаум и срок, без ФИО |
| Журнал вызовов, открытий и проездов | Конфиденциальные | У партнера и в smart-home-db | - |
| Согласия на обработку биометрии | Конфиденциальные | smart-home-db | Признак "согласие есть" и его ID |
| ФИО, телефон, адрес собственника | Конфиденциальные | CRM ЖКУ | **Не передаются** |

## 4. Требования к безопасности

### 4.1. Правовые требования

| № | Требование |
| --- | --- |
| SEC-01 | С партнером заключается договор поручения на обработку ПДн (ч. 3 ст. 6 152-ФЗ): цели, перечень действий, меры защиты, право PropDevelopment на аудит, порядок удаления данных при расторжении |
| SEC-02 | Все ПДн, биометрия и видеозаписи хранятся и обрабатываются только на территории РФ (ч. 5 ст. 18 152-ФЗ). Трансграничная передача запрещена |
| SEC-03 | Биометрия обрабатывается только с отдельного согласия в письменной форме (ст. 11 152-ФЗ): электронный документ с электронной подписью или бумажный бланк. Согласие дает каждый взрослый жилец, за ребенка - законный представитель |
| SEC-04 | Биометрия добровольна. У жильца всегда есть другой способ войти: открытие из приложения, ключ, код. Отказ от биометрии не ограничивает остальные услуги (ч. 3 ст. 11 152-ФЗ) |
| SEC-05 | До запуска юристы дают заключение о применимости 572-ФЗ (единая биометрическая система) к распознаванию лиц на домофоне. Если закон применим, распознавание идет через ЕБС или аккредитованную организацию |
| SEC-06 | После отзыва согласия или выезда жильца партнер удаляет шаблон в течение 24 часов и присылает подтверждение. Срок по закону - не более 30 дней (ч. 5 ст. 21 152-ФЗ), внутренний срок короче |
| SEC-07 | Лица посторонних и гостей не сравниваются с базой и не сохраняются как шаблоны. На входах размещается информация о видеонаблюдении и распознавании |
| SEC-08 | Партнер подтверждает выполнение мер защиты по приказу ФСТЭК N 21 для нужного уровня защищенности и ежегодно предоставляет отчет о тестировании на проникновение |

## 5. Протоколы аутентификации и авторизации

| Взаимодействие | Аутентификация | Авторизация |
| --- | --- | --- |
| Мобильное приложение -> smart-home-app | OpenID Connect, Authorization Code + PKCE через Keycloak (auth-service-1). Короткий access token (JWT) и refresh token. Для открытия - повторное подтверждение на устройстве | Роли (собственник, жилец, гость) плюс атрибуты (квартира, дом, подъезд) - проверка в smart-home-app |
| smart-home-app -> API-шлюз -> платформа партнера | mTLS между шлюзом и партнером + OAuth 2.0 Client Credentials | Scopes `access-rules:write`, `commands:open`, `calls:token`. Клиент привязан к списку ЖК |
| Платформа партнера -> API-шлюз -> smart-home-app (события) | mTLS + подпись HMAC-SHA256 + белый список IP | Проверка, что объект события принадлежит этому партнеру |
| Мобильное приложение -> медиасервер партнера (видеовызов) | Одноразовый токен вызова. smart-home-app получает его у партнера и передает приложению, срок жизни 60 секунд | Токен действует только для одного вызова и одной квартиры |
| Мобильное приложение -> партнер (загрузка фото) | Одноразовый токен регистрации. Выдается после фиксации согласия, срок жизни 5 минут | Токен действует для одного жильца и одной загрузки |
| smart-home-app -> CRM ЖКУ | OAuth 2.0 Client Credentials (сервисная учетная запись в Keycloak), внутри кластера - mTLS | Только чтение состава жильцов и подписка на события смены собственника |
| tenant-core-app -> API-шлюз -> УК и поставщики ЖКХ | mTLS + OAuth 2.0 Client Credentials, отдельный клиент на каждую УК | Проверка принадлежности объекта к УК в шлюзе и в сервисе |
| Диспетчер УК -> консоль партнера | SSO (OpenID Connect или SAML) + MFA | Роли в консоли, доступ только к домам своей УК |
| Платформа партнера -> устройства в ЖК | Сертификат X.509 на каждое устройство, VPN или mTLS | Устройство принимает команды только от платформы |
| API-шлюз, smart-home-app -> Vault | Kubernetes auth (сервисный аккаунт пода) | Политики Vault: каждый сервис читает только свои секреты |

## 6. Как организовано взаимодействие

### 6.1. Общие правила

- Контракты описываются заранее: REST - в OpenAPI 3, события - в AsyncAPI. До подписания контракты проходят ревью ИБ: нет лишних полей, ПДн только из согласованного списка.
- Версии API указываются в пути (`/v1/...`). Старая версия поддерживается не меньше 6 месяцев после выхода новой.
- Команды к партнеру идемпотентны (заголовок `Idempotency-Key`). При ошибках - повтор с увеличивающейся паузой, при серии ошибок - circuit breaker. Таймаут на команду открытия - 2 секунды.
- Изменения прав smart-home-app сначала записывает в свою БД, а партнеру отправляет через outbox. Так изменение не теряется при сбое сети.
- События партнера smart-home-app принимает асинхронно: сначала сохраняет, потом обрабатывает. Повторы отсекаются по event_id.

### 6.2. Основные сценарии

**Подключение ЖК.** Партнер устанавливает оборудование и регистрирует устройства. В smart-home-app заводится соответствие объектов: дом, подъезд, шлагбаум и их ID у партнера. В шлюзе партнерский клиент привязывается к этим объектам.

**Регистрация лица жильца.**
1. Собственник в приложении добавляет себя или члена семьи и подписывает согласие на биометрию.
2. smart-home-app сохраняет согласие и запрашивает у партнера одноразовый токен регистрации.
3. Приложение отправляет фото напрямую партнеру с этим токеном.
4. Партнер создает шаблон, удаляет фото и присылает событие `enrollment.completed` с псевдонимным ID.

**Открытие двери по вызову.**
1. Гость звонит в квартиру. Партнер присылает событие `call.started`.
2. smart-home-app определяет жильцов квартиры и через шлюз отправляет push без ПДн ("Входящий вызов").
3. Приложение получает токен вызова и подключается к видеопотоку партнера.
4. Жилец нажимает "Открыть" и подтверждает действие на телефоне. smart-home-app проверяет право и отправляет команду партнеру.
5. Партнер открывает замок и присылает событие `door.opened`, которое записывается в журнал.

**Автоматическое открытие по лицу.** Камера передает кадр платформе партнера. Партнер сравнивает лицо только с жильцами этого подъезда, при совпадении открывает дверь и присылает событие `access.granted` (псевдоним, объект, время, уверенность распознавания). Если совпадения нет, кадр не сохраняется.

**Въезд по номеру.** Собственник добавляет номер в приложении. smart-home-app проверяет формат и лимит, сохраняет номер и отправляет партнеру правило "номер - шлагбаум - срок". Камера распознает номер, шлагбаум открывается, приходит событие `barrier.opened`.

**Отзыв доступа.** CRM ЖКУ отправляет событие о смене собственника или выезде жильца. smart-home-app отзывает права квартиры и отправляет партнеру удаление правил и шаблонов. Партнер подтверждает удаление событием. Расхождения находит ночная сверка.
